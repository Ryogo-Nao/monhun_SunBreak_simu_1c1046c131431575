# UIの基本

## 1. 分かりやすさの3段階

UIの分かりやすさは次の3段階に分けて考える。

1. **押すと何が起こるか分かる**: ラベルやボタンの文言だけで、操作の結果が分かる。
2. **使ってみて分かる**: 押した結果が画面にすぐ表れ、試せば理解できる。
3. **説明があって分かる**: 文章で読まないと分からない。

**通常の画面は 1 と 2 だけで成り立たせる。3（説明文）は通常の画面に置かず、説明画面に分ける。**

説明文が多いと情報過多になり、画面が読みにくくなる。

## 2. 画面上の文言のルール

- ボタン・スイッチ・選択肢・見出しは、**できる限り短く**する。結果が分かる最小限の語にする。
- スイッチの下の補足（`<small>` など）、カード内の注意書き、使い方の段落は置かない。説明画面へ移す。
- 空の状態の表示も短くする（例:「未登録」「まだ検索していません」「該当なし」）。
- 件数などの状態は、文章ではなく小さな数値で添える（例:「傀異錬成防具を使う 0件」）。

| 長い（避ける） | 短い（推奨） |
| --- | --- |
| 所持していない防具・武器・固定護石も対象にする | 未所持の装備も使う |
| 装飾品の所持数を考慮する | 装飾品の所持数を反映 |
| この条件で検索 | 検索 |
| 表示中をすべて所持にする | 表示中を所持に |
| 他1件の同等装備 | 同等+1 |
| 最大件数に達したため探索を打ち切りました。… | 最大件数で打ち切り |

**例外**: 入力形式など、使ってみても分からないうえ、ないと操作できない情報は1行だけ残してよい（例: CSVの列順）。残すかどうか迷ったら、ユーザーに確認する。

## 3. 説明画面

- 各画面の**ヘッダーに説明ボタン（「？」）**を置く。
- 押すと、**いま表示している画面の説明**を開く。サブタブがある画面では、そのサブタブの説明を開く。
- 説明画面の上部に画面ごとの切り替えタブを置き、他の画面の説明も見られるようにする。
- 「← 戻る」や「？」の再押下で、**元の画面の元のスクロール位置**に戻す。
- 画面から外した説明文は、説明画面に**漏れなく移す**（削除して終わりにしない）。
- 対象（ゲームタイトル・モードなど）で内容が変わる場合は、説明も切り替える。
- 説明画面の中身は1か所（例: `helpBody(key)` のような関数）にまとめ、文言を直しやすくする。

## 4. 入力フォーム

### 4-1. 入力値は「ユーザーが見ている実際の値」で入れさせる

- **ユーザーが手元（ゲーム画面・書類など）で見ている値を、見えている形のまま入力させる。** 自分で計算しないと入れられない入力をさせない。
  - 手元に最終値が表示されるなら最終値を入れさせる（差分が内部で必要なら、保存時にプログラム側で計算する）。
  - 手元に**増減が表示される**なら増減を入れさせる（例: 傀異錬成の防御・耐性はゲーム画面に「防御+12」「火-2」と出るので増減で入力）。合計値は入力欄の下に小さく表示する。
  - どちらの形で表示されるか分からないときは、推測せずユーザーに確認する。
  - マイナスがありうる数値は、iPhone の数字キーボードにマイナスがないため、プルダウン（上ほど大きい値）にする。
- **編集の起点には既定値を入れておく。** ベースとなるもの（例: 元の防具）を選んだら、その値（スロット・スキル・防御など）を初期値として表示し、ユーザーは変わったところだけ直す。
- 「〜後」「〜変化」など、画面の文脈で明らかな修飾語は付けない（例: 錬成画面の「錬成後スロット」→「スロット」、「スキル変化」→「スキル」）。
- 意味が一目で分からないショートカットボタン（例:「精霊の加護 −1」）は置かない。操作は「Lvを変える」「✕で外す」「＋追加」のような基本操作で表す。

- **名前の文字入力（インポートなど）は、あいまい検索で照合する。** 完全一致を求めない（一部・読み・記号の省略・全角半角の違いを許す）。1つに決まるもの（完全一致、前方一致が1件、候補が1件）だけ自動で決め、**候補が複数・0件なら保存前に選び直してもらう**（あいまいなまま保存しない）。同じ入力は1回選べば全行に使う。
- **保存時に重複をチェックする。** メモなどを除いた中身が同じものが既にあれば、手入力の保存では確認を出し、一括取り込みでは既定で除外して件数を示す（取り込むかは選べる）。新しい登録画面を作るときも同じにする。

### 4-2. レイアウトを統一する

- **ラベルは入力欄の上、入力欄は全幅**を基本形にする。ラベルを横に並べる形は、長いラベルが2行に折り返したり、入力欄が次の行へ回り込んだりして崩れやすい。
- **折り返しそうな並びは、最初から段（グリッド）で組む。** 横に並べる個数を決め、等幅の列にする（例: スロット3つ＝3列、耐性5種＝5列で、各列の上に小さなラベル）。項目の一部だけが次の行に落ちる配置にしない。
- **同じ種類の入力は、同じ大きさ・同じ並びにする**（スロット選択はどの画面でも3列、スキル行はどの画面でも「名前｜Lv｜✕」など）。
- **関係する項目をまとまり（区画）で区切る。** 見出し付きの枠で分ける（例: ベース防具／スロット／スキル／防御・耐性／メモ）。参照用の情報（元の値など）と入力欄を同じ区画に混ぜない。
- 結果のプレビューは、入力欄そのものが結果を表している場合は置かない（二重表示になる）。

### 4-3. プルダウンの並び順

- **数値のプルダウンは「上ほど大きい値」（降順）で統一する。** スキルLv、スロットLv、件数など、すべて同じ向きにする。「なし」は一番下。
- プラス／マイナスがある場合も、上がプラス（大きい値）、下がマイナス。

### 4-4. ソフトウェアキーボードで隠さない

iOS では、キーボードが出ても `position: fixed` の要素は画面全体を基準にしたままなので、**下から出るシートや下寄せの入力欄がキーボードの裏に隠れる**。

- `window.visualViewport`（実際に見えている領域）の `height` と `offsetTop` を CSS 変数に流し、シートやオーバーレイの位置・高さをその中に収める。
- キーボード表示中（`innerHeight - visualViewport.height` が大きいとき）は `<html>` にクラス（例: `kb-open`）を付け、下部タブバーや下固定のボタンを隠して表示領域を広げる。
- 入力欄にフォーカスしたら、キーボードが出終わったころ（300〜400ms 後）に `scrollIntoView({ block: "nearest" })` で入力欄を見える位置へ動かす。
- 絞り込み検索のように、入力に応じて一覧が変わる画面では、**検索欄は一番上、結果はその下**に置き、キーボードの上の領域に収める。

```js
function syncViewport() {
  const vv = window.visualViewport; if (!vv) return;
  const root = document.documentElement;
  root.style.setProperty("--vv-h", vv.height + "px");
  root.style.setProperty("--vv-top", vv.offsetTop + "px");
  root.classList.toggle("kb-open", window.innerHeight - vv.height > 120);
}
visualViewport.addEventListener("resize", syncViewport);
visualViewport.addEventListener("scroll", syncViewport);
```

```css
.modal-back { position: fixed; left: 0; right: 0; top: var(--vv-top, 0px); height: var(--vv-h, 100%); }
:root.kb-open .modal { max-height: calc(var(--vv-h) - 8px); }
:root.kb-open .tabbar { display: none; }
```

- 確認は**すべての入力欄**で行う（ページ上の検索欄、各登録フォーム、選択モーダルの検索欄、フォーム下部のメモ欄など）。エミュレーションでは `visualViewport` を縮めるモックで位置を確かめ、最終確認は実機で行ってもらう（第6節）。

## 5. スマホ（iPhone）表示

- 確認する幅は、ユーザー指定の端末（例: iPhone 15 Plus）の幅にする。**横方向のはみ出しがないこと**を全画面で確かめる。
- 長い選択肢を含む `<select>` は、幅が内容に引きずられて画面がはみ出しやすい。`flex: 1 1 0; width: 0; min-width: 0;` で対策し、グリッドの子要素に `min-width: 0` を付ける。
- 入力欄の文字サイズは 16px 以上にする（iOSの自動ズーム防止）。
- 下部タブバー・上部ヘッダーの位置は、**内容の短い画面と長い画面の両方**で確かめる。

### iPhone のホーム画面アプリ（PWA）の既知の問題と対策

`apple-mobile-web-app-status-bar-style: black-translucent` と `viewport-fit=cover` を使う場合:

| 症状 | 原因 | 対策 |
| --- | --- | --- |
| 内容が短い画面だけ、下部の固定タブバーが上にずれる | スクロールしないページでは、固定要素の基準がステータスバー分だけ短くなる | `html { min-height: calc(100% + env(safe-area-inset-top)); }` と `body { min-height: calc(100vh + env(safe-area-inset-top)); }` |
| ステータスバー部分に白いモヤがかかり、時計の文字が黒くなる | iOS はステータスバーの色を、最上部の固定要素やページ背景から取る | ヘッダーを `position: fixed; top: 0` にする。`html` の背景をヘッダー色にし、本文の背景は `body` に付ける |
| タイトルがステータスバーのぼかしにかかる | ヘッダー内容がステータスバーに近すぎる | ホーム画面アプリ時だけ、ステータスバーの下に余白を足す（下記） |

```css
:root {
  --appbar-h: 48px;
  --safe-top: env(safe-area-inset-top);
  --top-extra: 0px;
  --appbar-total: calc(var(--appbar-h) + var(--safe-top) + var(--top-extra));
}
@media (display-mode: standalone) {
  :root { --safe-top: max(env(safe-area-inset-top), 54px); --top-extra: 14px; }
}
.appbar { position: fixed; top: 0; left: 0; right: 0; height: var(--appbar-total);
          padding: calc(var(--safe-top) + var(--top-extra)) 16px 0; }
body { padding-top: var(--appbar-total); }
```

`navigator.standalone` で `<html>` に `standalone` クラスを付ける保険も入れる。

## 6. 環境依存の調整は、必ずユーザーに実機確認を促す

ヘッダー／フッターの位置、ステータスバー周りの見た目、セーフエリアの扱い、キーボード表示時の配置は、**iOS のバージョン・端末・ホーム画面アプリかブラウザか**で変わる。ブラウザのエミュレーションでは再現できない。

これらを調整したときは、完了報告で必ず次のことをする。

1. **実機確認していないことを明記する**（「エミュレーションでの確認までです」など）。
2. **ユーザーに実機での確認を依頼する。** 見てほしい点を具体的に書く（例: ステータスバー部分がヘッダー色か、時計の文字が白か、タブバーが全画面で最下部か）。
3. **反映の手順を伝える**: ホーム画面アプリを完全に終了して開き直す。変わらなければアイコンを削除して Safari から追加し直す。オフラインキャッシュを使っている場合は、キャッシュ名（バージョン）を上げておく。
4. **調整つまみを伝える**: 例「余白は `css/style.css` の `--top-extra`（現在14px）で調整できます」。
5. **うまくいかない場合はスクリーンショットを依頼する。** 他のアプリで問題のない画面があれば、参考として見せてもらう。

## 7. 仕上げのチェックリスト

- [ ] 画面上に説明文の段落・補足がない（説明画面に移した）
- [ ] ボタン・スイッチ・選択肢の文言が最短になっている
- [ ] 全画面のヘッダーから説明ボタンで説明画面に行け、戻ると元の位置に戻る
- [ ] 外した説明が説明画面に漏れなくある
- [ ] 指定端末の幅で、全画面に横はみ出しがない
- [ ] 内容の短い画面と長い画面で、ヘッダー・タブバーの位置が同じ
- [ ] 入力は実際の値で入れられる（差分・増減の入力をさせていない）。編集の起点に既定値が入っている
- [ ] フォームはラベル上・入力欄全幅、区画で区切られ、同じ種類の入力が同じ大きさ・並び
- [ ] 横並びの項目が中途半端に折り返していない（段で組んである）
- [ ] 数値のプルダウンがすべて降順（上ほど大きい値）
- [ ] すべての入力欄で、キーボード表示時に入力欄・シートが隠れない
- [ ] 指摘された修正を、同じ種類の箇所すべてに漏れなく適用した（1画面だけ直して終わりにしない）
- [ ] 環境依存の調整をした場合、ユーザーに実機確認を依頼した（第6節）
- [ ] 押せる部品は高さ44px相当（小さく見せたいボタンは透明な当たり判定で広げる）
- [ ] 文字のコントラスト4.5:1以上、スイッチなど文字以外の部品は3:1以上（ライト・ダーク両方）
- [ ] アイコンは絵文字でなくインラインSVG。外部のフォント・CDN・アイコンライブラリは使わない
- [ ] 通知（トースト）は3〜5秒表示。端末の「動きを減らす」設定で動きを止める
- [ ] 登録・編集画面は、入力後に外側を押しても確認なしでは閉じない。Escで閉じられる

## 8. 一般的なUI基準の参照
