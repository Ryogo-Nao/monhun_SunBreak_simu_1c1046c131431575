# UIの基本

## 1. 分かりやすさの3段階

UIの分かりやすさは次の3段階に分けて考える。

1. **押すと何が起こるか分かる**: ラベルやボタンの文言だけで、操作の結果が分かる。
2. **使ってみて分かる**: 押した結果が画面にすぐ表れ、試せば理解できる。
3. **説明があって分かる**: 文章で読まないと分からない。

**通常の画面は 1 と 2 だけで成り立たせる。3（説明文）は通常の画面に置かず、説明画面に分ける。**

説明文が多いと情報過多になり、画面が読みにくくなる。

## 2. 画面上の文言のルール

- ボタン・スイッチ・選択肢・見出しは、**できる限り短く**する。結果が分かる最小限の語にする。
- スイッチの下の補足（`<small>` など）、カード内の注意書き、使い方の段落は置かない。説明画面へ移す。
- 空の状態の表示も短くする（例:「未登録」「まだ検索していません」「該当なし」）。
- 件数などの状態は、文章ではなく小さな数値で添える（例:「傀異錬成防具を使う 0件」）。

| 長い（避ける） | 短い（推奨） |
| --- | --- |
| 所持していない防具・武器・固定護石も対象にする | 未所持の装備も使う |
| 装飾品の所持数を考慮する | 装飾品の所持数を反映 |
| この条件で検索 | 検索 |
| 表示中をすべて所持にする | 表示中を所持に |
| 他1件の同等装備 | 同等+1 |
| 最大件数に達したため探索を打ち切りました。… | 最大件数で打ち切り |

**例外**: 入力形式など、使ってみても分からないうえ、ないと操作できない情報は1行だけ残してよい（例: CSVの列順）。残すかどうか迷ったら、ユーザーに確認する。

## 3. 説明画面

- 各画面の**ヘッダーに説明ボタン（「？」）**を置く。
- 押すと、**いま表示している画面の説明**を開く。サブタブがある画面では、そのサブタブの説明を開く。
- 説明画面の上部に画面ごとの切り替えタブを置き、他の画面の説明も見られるようにする。
- 「← 戻る」や「？」の再押下で、**元の画面の元のスクロール位置**に戻す。
- 画面から外した説明文は、説明画面に**漏れなく移す**（削除して終わりにしない）。
- 対象（ゲームタイトル・モードなど）で内容が変わる場合は、説明も切り替える。
- 説明画面の中身は1か所（例: `helpBody(key)` のような関数）にまとめ、文言を直しやすくする。

## 4. スマホ（iPhone）表示

- 確認する幅は、ユーザー指定の端末（例: iPhone 15 Plus）の幅にする。**横方向のはみ出しがないこと**を全画面で確かめる。
- 長い選択肢を含む `<select>` は、幅が内容に引きずられて画面がはみ出しやすい。`flex: 1 1 0; width: 0; min-width: 0;` で対策し、グリッドの子要素に `min-width: 0` を付ける。
- 入力欄の文字サイズは 16px 以上にする（iOSの自動ズーム防止）。
- 下部タブバー・上部ヘッダーの位置は、**内容の短い画面と長い画面の両方**で確かめる。

### iPhone のホーム画面アプリ（PWA）の既知の問題と対策

`apple-mobile-web-app-status-bar-style: black-translucent` と `viewport-fit=cover` を使う場合:

| 症状 | 原因 | 対策 |
| --- | --- | --- |
| 内容が短い画面だけ、下部の固定タブバーが上にずれる | スクロールしないページでは、固定要素の基準がステータスバー分だけ短くなる | `html { min-height: calc(100% + env(safe-area-inset-top)); }` と `body { min-height: calc(100vh + env(safe-area-inset-top)); }` |
| ステータスバー部分に白いモヤがかかり、時計の文字が黒くなる | iOS はステータスバーの色を、最上部の固定要素やページ背景から取る | ヘッダーを `position: fixed; top: 0` にする。`html` の背景をヘッダー色にし、本文の背景は `body` に付ける |
| タイトルがステータスバーのぼかしにかかる | ヘッダー内容がステータスバーに近すぎる | ホーム画面アプリ時だけ、ステータスバーの下に余白を足す（下記） |

```css
:root {
  --appbar-h: 48px;
  --safe-top: env(safe-area-inset-top);
  --top-extra: 0px;
  --appbar-total: calc(var(--appbar-h) + var(--safe-top) + var(--top-extra));
}
@media (display-mode: standalone) {
  :root { --safe-top: max(env(safe-area-inset-top), 54px); --top-extra: 14px; }
}
.appbar { position: fixed; top: 0; left: 0; right: 0; height: var(--appbar-total);
          padding: calc(var(--safe-top) + var(--top-extra)) 16px 0; }
body { padding-top: var(--appbar-total); }
```

`navigator.standalone` で `<html>` に `standalone` クラスを付ける保険も入れる。

## 5. 環境依存の調整は、必ずユーザーに実機確認を促す

ヘッダー／フッターの位置、ステータスバー周りの見た目、セーフエリアの扱いは、**iOS のバージョン・端末・ホーム画面アプリかブラウザか**で変わる。ブラウザのエミュレーションでは再現できない。

これらを調整したときは、完了報告で必ず次のことをする。

1. **実機確認していないことを明記する**（「エミュレーションでの確認までです」など）。
2. **ユーザーに実機での確認を依頼する。** 見てほしい点を具体的に書く（例: ステータスバー部分がヘッダー色か、時計の文字が白か、タブバーが全画面で最下部か）。
3. **反映の手順を伝える**: ホーム画面アプリを完全に終了して開き直す。変わらなければアイコンを削除して Safari から追加し直す。オフラインキャッシュを使っている場合は、キャッシュ名（バージョン）を上げておく。
4. **調整つまみを伝える**: 例「余白は `css/style.css` の `--top-extra`（現在14px）で調整できます」。
5. **うまくいかない場合はスクリーンショットを依頼する。** 他のアプリで問題のない画面があれば、参考として見せてもらう。

## 6. 仕上げのチェックリスト

- [ ] 画面上に説明文の段落・補足がない（説明画面に移した）
- [ ] ボタン・スイッチ・選択肢の文言が最短になっている
- [ ] 全画面のヘッダーから説明ボタンで説明画面に行け、戻ると元の位置に戻る
- [ ] 外した説明が説明画面に漏れなくある
- [ ] 指定端末の幅で、全画面に横はみ出しがない
- [ ] 内容の短い画面と長い画面で、ヘッダー・タブバーの位置が同じ
- [ ] 環境依存の調整をした場合、ユーザーに実機確認を依頼した（第5節）
